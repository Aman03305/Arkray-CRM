# API conventions

Applies to every endpoint under `/api/v1`. The OpenAPI schema is generated by
drf-spectacular (`uv run python manage.py spectacular --file schema.yaml`); from Phase 1 the
frontend's request and response types are generated from it.

## Basics

- JSON only (`application/json`), UTF-8, `snake_case` fields. A `charset` other than
  UTF-8 is `415` (the body is never decoded with a client-named codec: that allowed
  compression "codecs" to inflate a small body into gigabytes, found in the Phase 2 review);
  pathologically nested JSON is `400 malformed_request`. Responses are ASCII-escaped JSON.
- **No trailing slashes** (`/api/v1/workspaces/me/leads`). Next.js strips trailing slashes
  before proxying, and Django's `APPEND_SLASH` is off.
- Versioning: breaking changes → `/api/v2`. Additive changes (new optional fields,
  endpoints or filters) stay in v1; clients must ignore unknown fields.
- Session-cookie auth; unsafe methods need `X-CSRFToken`, signed in or not
  ([authorization.md](authorization.md#mechanism)). Views derive from `core.api.ApiView`,
  which enforces this and marks every response `Cache-Control: no-store`.
- **Strict request bodies:** input serializers derive from `StrictInputSerializer`, so an
  undeclared key gets a 400 (`Unknown field(s): …`) instead of being silently ignored.
  Query parameters are validated the same way, and endpoints that read none refuse any
  (`?owner=…` on a create is a 400, never silently ignored).
- The OpenAPI schema is committed as `backend/openapi.yaml` (a test fails if it drifts),
  and the frontend's types are generated from it (`pnpm api:types`; CI runs
  `pnpm api:check`).

## Resource layout

```
/api/v1/auth/csrf | login | logout | me           session (Phase 1)
/api/v1/auth/password/change | password-reset[/confirm]
/api/v1/auth/invitations/verify | accept
/api/v1/admin/users[/{id}]                        user management (users.manage)
/api/v1/admin/users/{id}/activate|deactivate|resend-invitation|change-email
/api/v1/workspaces/{workspace}                    whose workspace this is (audited when delegated)
/api/v1/admin/audit-events                        audit log (audit.view)
/api/v1/config/pipelines                          pipelines with their stages (GET, any user; Phase 3)
/api/v1/config/lead-options                       statuses, sources, ratings, countries (Phase 2)
/api/v1/assignees?q=                             users records can be assigned to (crm.assign_any; Phase 2)

/api/v1/workspaces/{workspace}/dashboard              (Phase 5; `all` is the Admin Home)
/api/v1/workspaces/{workspace}/leads[/{id}]            (Phase 2)
/api/v1/workspaces/{workspace}/leads/duplicates        (Phase 2)
/api/v1/workspaces/{workspace}/leads/{id}/status | assign | archive | restore   (Phase 2)
/api/v1/workspaces/{workspace}/leads/{id}/timeline     (Phase 4)
/api/v1/workspaces/{workspace}/leads/{id}/convert           (Phase 3)
/api/v1/workspaces/{workspace}/pipeline-board | pipeline-summary   (Phase 3)
/api/v1/workspaces/{workspace}/opportunities[/{id}]         (Phase 3)
/api/v1/workspaces/{workspace}/opportunities/{id}/move | archive | restore | history   (Phase 3)
/api/v1/workspaces/{workspace}/opportunities/{id}/timeline  (Phase 4)
/api/v1/workspaces/{workspace}/activities[/{id}]      ?type=task|meeting|note
/api/v1/workspaces/{workspace}/activities/{id}/complete | cancel
/api/v1/workspaces/{workspace}/search?q=
/api/v1/workspaces/{workspace}/ask
```

`{workspace}` is `me`, `all` or a user UUID. It is resolved and authorised server-side on
every request ([authorization.md](authorization.md#admin--user-workspace-built-resolution-ui-in-phase-6)).
Tasks, meetings and notes share the `activities` resource with a `type` discriminator, one
schema per type in OpenAPI; per-type convenience routes can be added later without new
business logic.

## Methods and status codes

| Method | Use |
|---|---|
| `GET` | list / retrieve |
| `POST` | create (**201** + `Location`), or an **action** sub-resource (`/move`, `/assign`, `/complete`) |
| `PATCH` | partial update; body must include the current `version` |
| `PUT` | not used |
| `DELETE` | not used for CRM records (they are archived via `/archive`); reserved for truly disposable resources |

| Code | Meaning |
|---|---|
| 200 / 201 / 204 | success |
| 400 `validation_error` / `malformed_request` | invalid input (field details included) |
| 401 `not_authenticated` | no or expired session (with `WWW-Authenticate: Session realm="arkray"`) |
| 400 `invalid_credentials` / `invalid_token` | failed sign-in (always the same body) / unusable emailed link |
| 403 `permission_denied` / `csrf_failed` | authenticated but lacking a capability; CSRF failure |
| 404 `not_found` | does not exist **or is outside your scope** (deliberately indistinguishable) |
| 405, 406, 415 | method / accept / media type |
| 409 `conflict` | stale `version` or uniqueness conflict: reload and retry |
| 422 `business_rule_violation` | valid shape, but not allowed (for example, moving a won deal without reopening) |
| 429 `rate_limited` | throttled; `Retry-After` header |
| 500 `server_error` | unexpected; never contains internals |
| 503 `service_unavailable` / `ai_unavailable` | optional dependency down |

## Error envelope

Every error, from DRF, from domain services or from Django's 404/500 handlers, has one shape:

```json
{"error": {"code": "validation_error", "message": "Some fields are invalid.",
           "details": {"email": ["Enter a valid email address."]},
           "request_id": "0d531bcf758a4961814b728020d9b042"}}
```

`code` is stable and machine-readable; `message` is safe to show; `request_id` matches the
`X-Request-ID` header and the server logs.

## Pagination

- Lists use **cursor (keyset) pagination** by default:
  `{"results": [...], "next": "<url|null>", "previous": "<url|null>"}`. CRM lists
  (from Phase 2) use `core.keyset`: the cursor holds the whole sort key of the boundary
  row, is signed and bound to the ordering, and handles ties and NULLs exactly
  ([ADR-0016](adr/0016-composite-keyset-pagination.md)). A malformed, forged or
  other-ordering cursor is `400 validation_error` on `cursor`. No counts are returned.
- `page_size` defaults to 25, maximum 100. There are no unbounded lists; small
  configuration lists (stages, statuses) may be returned whole.
- Each list's ordering ends in a unique column (`-created_at, -id`) so cursors are stable.

## Filtering, sorting, search

- **Allowlisted per endpoint.** Every filter is declared explicitly (leads: `status`,
  `source`, `rating`, `created_from`, `created_to` (inclusive business days), `archived`,
  and `owner` only in the `all` workspace, [leads.md](leads.md#search-filters-sorting)). **Unknown query parameters return 400** so client
  bugs and probing are visible. No generic ORM lookups (`?owner__email__contains=`) are ever
  accepted.
- `ordering` accepts only listed values (leads: `-created_at`, `created_at`, `name`,
  `-updated_at`, `-last_contacted_at`, `last_contacted_at`), each backed by an index.
- `q` search: 2–100 characters, up to 5 terms that must all match, scoped like everything
  else. Module lists search their own fields (leads: names, organisation, email, phone
  digits via a trigram index); global search across modules is Phase 7.

## Data formats

| Type | Format |
|---|---|
| IDs | UUID strings |
| Money | decimal **string** with 2 places: `"1000000.00"`; currency echoed in aggregate payloads (`"INR"`). **Input**: a string of plain digits with at most 2 decimals, or an integer; JSON numbers with a fraction, exponents, signs, separators, NaN/Infinity and non-ASCII digits are a 400 (`core.api.ExactDecimalField`) |
| Probability | decimal string `"50.00"`; input like money (0-100) |
| Timestamps | ISO 8601 UTC with offset: `"2026-09-30T10:15:00Z"` |
| Dates | `"2026-09-30"` |
| Enums | lower-case strings (`"open"`, `"won"`, `"task"`) |
| Related records | `{"id": "…", "label": "…"}`; `{"id": null, "restricted": true}` if not visible |

## Concurrency

Editable resources include `version`. `PATCH` without it → 400; with a stale value → 409.

## Idempotency

`POST` create endpoints where a double submit is harmful (lead create from Phase 2;
opportunity create and lead conversion from Phase 3; CSV import later) accept an `Idempotency-Key` header (canonical UUID; anything else is a 400).
The key, the actor, the operation, a SHA-256 of the validated request and the created
record's id are stored in PostgreSQL (`core_idempotency_record`) for 24 h, never the
body. A replay returns `201` with the record's current representation and
`Idempotent-Replayed: true`; the same key with a different body → `422
idempotency_key_reused`. Keys are private to each actor. Concurrent requests with one
key create one record. Action endpoints are naturally idempotent where possible (moving to
the current stage is a no-op).

## Rate limits

Defaults: anonymous 60/min, authenticated 600/min. Scoped: login and password reset
(strict, PostgreSQL-backed for login), `search` 60/min, `ask` 20/min and 300/day, import
10/hour.

## Checklist for a new endpoint

1. Nest CRM endpoints under `/workspaces/{workspace}/` and resolve the scope first.
2. Declare `permission_classes` explicitly (the default is `DenyAll`).
3. Query only through scoped selectors; return 404 outside scope.
4. Explicit serializer fields; no writable ownership, status or timestamps.
5. Allowlisted filters and ordering; bounded pagination.
6. Services own transactions, audit, timeline and outbox events.
7. Add the route to `tests/authz_matrix.py` and write the matrix, cross-user and query-count
   tests.
