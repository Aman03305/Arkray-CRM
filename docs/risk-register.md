# Architectural risk register

Risks identified before feature work, how the architecture resolves each one, and how the
resolution is verified. **Status** is either *Resolved (P0)* (mechanism built and tested in
Phase 0) or *Designed (Pn)* (mechanism fixed here, implemented and tested in phase *n*).

| # | Risk | Architectural resolution | Verification | Status |
|---|---|---|---|---|
| R1 | **Cross-user data leakage** | One scoping primitive (`AccessScope`) for every read path; scopes built only by `resolve_workspace()` from the authenticated actor; an empty owner set can never mean "all"; background jobs are the only unscoped readers and never serve users | `AccessScope` invariant tests; real-table filtering tests; cross-user suite per phase | Resolved (P0) primitive · Resolved (P2) leads · Resolved (P3) pipeline incl. aggregates · Designed (P4–P8) |
| R2 | **IDOR** | Workspace-nested routes; lookups only via `scope.apply()`; 404 (never 403) outside scope; `{uuid}` workspace 404s identical for "missing" and "forbidden" | enumeration-safety test in `test_workspaces.py`; route-inventory guard; per-endpoint matrix | Resolved (P0) gate · Resolved (P2) leads endpoints · Resolved (P3) pipeline endpoints · Designed (P4+) |
| R3 | **RAG authorization leakage** | Tools bound to the caller's scope server-side; no scope parameters in tool schemas; org tools absent for non-admins; vector pre-filter by `owner_id` **plus** live re-verification through scoped selectors; context text from live records | golden, cross-user, vector-leak and adversarial tests | Designed (P8) |
| R4 | **Inaccurate financial / pipeline figures** | `NUMERIC(14,2)` and `Decimal` end to end; money as JSON strings; SQL aggregates rounded once; won/lost probabilities fixed by CHECKs; status snapshot at transition; LLM never computes figures; numeric grounding check on AI narrative | architecture test bans `FloatField`; exact aggregate tests (₹1,000,000 × 50 % = ₹500,000.00; the brief's ₹15,00,000 / ₹9,00,000 example; rounding boundaries; 1,000 random amounts SQL = Python; 25 × the maximum value); strict decimal input; grounding tests | Resolved (P0) float ban · Resolved (P3) pipeline figures · Designed (P5, P8) |
| R5 | **Wrong "today"** (UTC vs IST) | Day boundaries in `CRM_TIME_ZONE`, computed server-side ([ADR-0012](adr/0012-business-day-time-zone.md)); tz-aware datetimes enforced (ruff `DTZ`, naive-datetime warnings are errors in tests) | midnight-boundary tests | Resolved (P0) tooling · Designed (P5) |
| R6 | **Race conditions** | `SELECT … FOR UPDATE` on stage moves and reassignment; `version` optimistic concurrency (409); DB constraints as final arbiter; outbox claims with `SKIP LOCKED`; deferrable unique stage positions | outbox concurrency-safe claim tests; threaded concurrency tests (P2: reassign × reassign, edit × edit, archive × edit, status × reassign, reassign × deactivation, idempotent double create) | Resolved (P0) outbox · Resolved (P2) leads · Resolved (P3) pipeline: row locks in one documented lead → opportunity → user order, versions, deferred composite keys; real-thread races (move × move, edit × edit, move × edit, archive × move, reassign × move/close/create, conversion × conversion, conversion × reassignment, a 12-writer storm) and interleavings built to deadlock on a wrong lock order |
| R7 | **N+1 queries** | Selectors own query shape (`select_related`/`prefetch_related`); admin tables aggregate with `GROUP BY owner_id` per page | exact query counts pinned for every leads endpoint at 10 and 100 rows (P2) and every pipeline endpoint (P3: board 7, list 3, detail 3, summary 3, history 4) | Resolved (P2) leads · Resolved (P3) pipeline · Designed (P4+) |
| R8 | **Unbounded queries / result sets** | Cursor pagination with max 100; allowlisted filters (unknown params → 400); statement timeout 10 s; imports and exports in workers | pagination default set globally (P0); composite keyset pagination with signed cursors (P2); 300k-lead benchmark and query-plan regression tests; the Kanban board returns at most 50 cards per stage (one UNION ALL of index-backed LIMITs) and continues in keyset pages (P3, 300k-opportunity benchmark) | Resolved (P0) defaults · Resolved (P2) leads · Resolved (P3) pipeline |
| R9 | **AI outage blocks the CRM** | No synchronous AI in CRM writes; indexing via outbox; Ask Arkray behind a circuit breaker and timeouts; `AI_ENABLED` kill switch | outbox atomicity and retry tests (P0); breaker tests (P8) | Resolved (P0) mechanism · Designed (P8) |
| R10 | **Redis / Celery outage** | Sessions and login throttling in PostgreSQL; cache failures are misses; **fail-fast cache connections** (no retries + circuit breaker); broker outage → outbox rows wait durably; readiness `degraded`, not failed | fast-miss test (50 ops against a dead Redis < 2 s); live drill: 8 s → 0.2 s per request; readiness tests; broker-failure relay test | Resolved (P0) |
| R11 | **Accidental admin impersonation** | No impersonation feature exists. Admin workspace = scoped access as the admin; the actor stays the admin in audit and `created_by`; the viewed user's session is never touched | `test_opens_a_users_workspace_scoped_to_that_user` asserts `actor_id == admin` | Resolved (P0) |
| R12 | **Unaudited admin access** | `workspace.accessed` audit at least once per actor/workspace per 15 min; the window marker is set only after the audit row commits; fails toward more auditing if the cache is down; every write audited individually | audit, de-duplication, rollback and cache-outage tests | Resolved (P0) |
| R13 | **Audit-history mutation** | `AppendOnlyModel` blocks ORM updates and deletes; PostgreSQL trigger blocks UPDATE/DELETE even from raw SQL; production app role lacks UPDATE/DELETE/TRUNCATE; audit has no FKs, so cascades can't touch it | ORM and raw-SQL tamper tests; guard test that every append-only model has its trigger | Resolved (P0) · roles (P11) |
| R14 | **DB connection exhaustion** | Documented connection budget; bounded per-process usage (sync workers, optional psycopg pool); PgBouncer in production; statement, lock and idle-in-transaction timeouts release stuck connections | settings in P0; load test (P10) | Resolved (P0) settings · Designed (P10) |
| R15 | **Cascading retry failures** | Exactly one retry layer (outbox); bounded attempts → dead; exponential backoff with jitter; per-queue in-flight caps; relay ticks expire; LLM SDK `max_retries=1` behind a breaker | retry, dead-letter, crash-loop, in-flight cap and backoff tests | Resolved (P0) |
| R16 | **Unbounded broker queues** | Durable backlog in PostgreSQL; Redis holds at most `OUTBOX_MAX_IN_FLIGHT` per queue; messages expire with their dispatch lease | in-flight cap test | Resolved (P0) |
| R16a | **Background pipeline jam / duplicate execution** (found by the Phase 0 review) | No unique constraint on pending work: best-effort coalescing only into never-attempted events, row-locked until the caller commits; claim tokens on every transition; dispatch and running leases; relay on a dedicated queue | regression tests: recovery with a pending duplicate, retry with a pending duplicate, stale and duplicate messages ignored, threaded pre-commit coalescing, relay routing; container round-trip | Resolved (P0) |
| R17 | **Endpoint added without authorization** | Global `DenyAll`; route inventory must match the authorization matrix | architecture tests (including a test that the guard detects an unregistered route) | Resolved (P0) |
| R18 | **Stale vector metadata after reassignment** | Re-verification against live ownership makes stale chunks harmless; reassignment enqueues re-index; nightly reconciliation | planted-stale-chunk test | Designed (P8) |
| R19 | **Prompt injection via CRM text** | Read-only scope-bound tools (nothing to escalate to); retrieved text treated as data; no exfiltration channel in rendered output | adversarial tests | Designed (P8) |
| R20 | **Secret leakage / weak production config** | env-only secrets; production refuses dev or short keys, missing hosts, a missing proxy count, and HTTPS weakening without an explicit local opt-in; WSGI defaults to production settings; secrets redacted from audit metadata; logs never include bodies, headers or query strings | production-settings tests; redaction tests; log tests | Resolved (P0) |
| R21 | **Module coupling decays into a big ball of mud** | Enforced layering (`import-linter`), services/selectors convention, cross-module work via outbox topics | `lint-imports` in CI (already caught one violation in P0) | Resolved (P0) |
| R22 | **Environment: repository inside OneDrive; Node 20 (EOL) installed** | Documented: move the repo outside OneDrive; use Node 24 LTS (project engines `>=22.12`, Docker `node:24`) | — | Open (action for the developer) |
| R24 | **Attacker-triggered account lockout (DoS)** (Phase 1) | Bounded exponential lockout (≤ 15 min); per-browser budgets via a signed trusted-device cookie, so the owner's usual browser is never locked by others; reset and activation clear lockouts | `test_a_trusted_browser_is_not_locked_out_by_an_attacker`, `test_lockouts_expire`, `test_a_reset_lifts_a_sign_in_lockout` | Resolved (P1) |
| R25 | **One-time link secrets leaking** (URL, DB, outbox, logs) (Phase 1) | 256-bit secrets minted in the email job; only SHA-256 stored; single use, expiry, supersession, purpose binding; no-referrer and no-store on link pages; proxy must not log those paths | `test_secret_hygiene.py`, `test_emails_a_one_time_link_and_stores_only_its_digest`; live check of headers | Resolved (P1) · proxy config (P11) |
| R26 | **Sessions revived after reactivation** (found while designing Phase 1: Django only suspends an inactive user's sessions) | `session_epoch` in the session auth hash, incremented on deactivation, email change and reset | `test_old_sessions_stay_dead_after_reactivation` | Resolved (P1) |
| R27 | **Races in account flows** (double activation, resend vs activation, two admins deactivating each other, admin deactivated mid-action) | One admin advisory lock with the actor re-read under it; user-then-token lock order; DB constraints (one pending token, unique email) | threaded tests in `identity/tests/test_concurrency.py` | Resolved (P1) |
| R28 | **An administrator can take over another account** by changing its email to a mailbox they control and resetting the password (Phase 1 review) | Accepted for v1: admins are fully trusted to manage identities.
