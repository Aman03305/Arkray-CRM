# Architectural risk register

Risks identified before feature work, how the architecture resolves each one, and how the
resolution is verified. **Status** is either *Resolved (P0)* (mechanism built and tested in
Phase 0) or *Designed (Pn)* (mechanism fixed here, implemented and tested in phase *n*).

| # | Risk | Architectural resolution | Verification | Status |
|---|---|---|---|---|
| R1 | **Cross-user data leakage** | One scoping primitive (`AccessScope`) for every read path; scopes built only by `resolve_workspace()` from the authenticated actor; an empty owner set can never mean "all"; background jobs are the only unscoped readers and never serve users | `AccessScope` invariant tests; real-table filtering tests; cross-user suite per phase | Resolved (P0) primitive · Resolved (P2) leads · Resolved (P3) pipeline incl. aggregates · Resolved (P4) activities, timelines (visibility per entry at read time) and counts · Designed (P5–P8) |
| R2 | **IDOR** | Workspace-nested routes; lookups only via `scope.apply()`; 404 (never 403) outside scope; `{uuid}` workspace 404s identical for "missing" and "forbidden" | enumeration-safety test in `test_workspaces.py`; route-inventory guard; per-endpoint matrix | Resolved (P0) gate · Resolved (P2) leads endpoints · Resolved (P3) pipeline endpoints · Resolved (P4) activity and timeline endpoints, incl. relationship fields (identical 404s) · Designed (P5+) |
| R3 | **RAG authorization leakage** | Tools bound to the caller's scope server-side; no scope parameters in tool schemas; org tools absent for non-admins; vector pre-filter by `owner_id` **plus** live re-verification through scoped selectors; context text from live records | golden, cross-user, vector-leak and adversarial tests | Designed (P8) |
| R4 | **Inaccurate financial / pipeline figures** | `NUMERIC(14,2)` and `Decimal` end to end; money as JSON strings; SQL aggregates rounded once; won/lost probabilities fixed by CHECKs; status snapshot at transition; LLM never computes figures; numeric grounding check on AI narrative | architecture test bans `FloatField`; exact aggregate tests (₹1,000,000 × 50 % = ₹500,000.00; the brief's ₹15,00,000 / ₹9,00,000 example; rounding boundaries; 1,000 random amounts SQL = Python; 25 × the maximum value); strict decimal input; grounding tests | Resolved (P0) float ban · Resolved (P3) pipeline figures · Designed (P5, P8) |
| R5 | **Wrong "today"** (UTC vs IST) | Day boundaries in `CRM_TIME_ZONE`, computed server-side ([ADR-0012](adr/0012-business-day-time-zone.md)); tz-aware datetimes enforced (ruff `DTZ`, naive-datetime warnings are errors in tests) | midnight-boundary tests | Resolved (P0) tooling · Resolved (P4) `core.business_time` with UTC-boundary tests (00:15 IST belongs to the new day); activity summary and date filters use it · Designed (P5) |
| R6 | **Race conditions** | `SELECT … FOR UPDATE` on stage moves and reassignment; `version` optimistic concurrency (409); DB constraints as final arbiter; outbox claims with `SKIP LOCKED`; deferrable unique stage positions | outbox concurrency-safe claim tests; threaded concurrency tests (P2: reassign × reassign, edit × edit, archive × edit, status × reassign, reassign × deactivation, idempotent double create) | Resolved (P0) outbox · Resolved (P2) leads · Resolved (P3) pipeline: row locks in one documented lead → opportunity → user order, versions, deferred composite keys; real-thread races (move × move, edit × edit, move × edit, archive × move, reassign × move/close/create, conversion × conversion, conversion × reassignment, a 12-writer storm) and interleavings built to deadlock on a wrong lock order · Resolved (P4) activities: lock order extended to lead → opportunities → activities → user rows; races for complete × complete, edit/cancel × complete, note edit × reassignment, creation × reassignment and × opportunity close, completion × reassignment, older × newer meeting completion (last contact never backwards), an 8-writer storm; a deliberate lock-order mutation produced `deadlock detected` |
| R7 | **N+1 queries** | Selectors own query shape (`select_related`/`prefetch_related`); admin tables aggregate with `GROUP BY owner_id` per page | exact query counts pinned for every leads endpoint at 10 and 100 rows (P2) and every pipeline endpoint (P3: board 7, list 3, detail 3, summary 3, history 4) | Resolved (P2) leads · Resolved (P3) pipeline · Resolved (P4) activities (list 3, detail 3, summary 3, lead timeline 5, opportunity timeline 4; reassignment 12 however much moves) · Designed (P5+) |
| R8 | **Unbounded queries / result sets** | Cursor pagination with max 100; allowlisted filters (unknown params → 400); statement timeout 10 s; imports and exports in workers | pagination default set globally (P0); composite keyset pagination with signed cursors (P2); 300k-lead benchmark and query-plan regression tests; the Kanban board returns at most 50 cards per stage (one UNION ALL of index-backed LIMITs) and continues in keyset pages (P3, 300k-opportunity benchmark) | Resolved (P0) defaults · Resolved (P2) leads · Resolved (P3) pipeline · Resolved (P4) activities and timelines (keyset pages ≤ 100 / ≤ 50; previews instead of whole notes; 403k-activity benchmark, query-plan tests) |
| R9 | **AI outage blocks the CRM** | No synchronous AI in CRM writes; indexing via outbox; Ask Arkray behind a circuit breaker and timeouts; `AI_ENABLED` kill switch | outbox atomicity and retry tests (P0); breaker tests (P8) | Resolved (P0) mechanism · Designed (P8) |
| R10 | **Redis / Celery outage** | Sessions and login throttling in PostgreSQL; cache failures are misses; **fail-fast cache connections** (no retries + circuit breaker); broker outage → outbox rows wait durably; readiness `degraded`, not failed | fast-miss test (50 ops against a dead Redis < 2 s); live drill: 8 s → 0.2 s per request; readiness tests; broker-failure relay test | Resolved (P0) |
| R11 | **Accidental admin impersonation** | No impersonation feature exists. | R13 | **Audit-history mutation** | `AppendOnlyModel` blocks ORM updates and deletes; PostgreSQL trigger blocks UPDATE/DELETE even from raw SQL; production app role lacks UPDATE/DELETE/TRUNCATE; audit has no FKs, so cascades can't touch it | ORM and raw-SQL tamper tests; guard test that every append-only model has its trigger | Resolved (P0) · roles (P11) |
| R14 | **DB connection exhaustion** | Documented connection budget; bounded per-process usage (sync workers, optional psycopg pool); PgBouncer in production; statement, lock and idle-in-transaction timeouts release stuck connections | settings in P0; load test (P10) | Resolved (P0) settings · Designed (P10) |
| R15 | **Cascading retry failures** | Exactly one retry layer (outbox); bounded attempts → dead; exponential backoff with jitter; per-queue in-flight caps; relay ticks expire; LLM SDK `max_retries=1` behind a breaker | retry, dead-letter, crash-loop, in-flight cap and backoff tests | Resolved (P0) |
